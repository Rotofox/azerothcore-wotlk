# Engineer-mandated decisions (carry verbatim)

1. **Container**: modify `modules/mod-random-enchants` in place. Never commit, push, or pull. The existing random-enchantment functionality stays alongside the quality system in the same module.
2. **Award events**: an item is rolled at four points — drop (loot), crafting/profession create, quest reward, and group-roll reward — all via the module's existing PlayerScript hooks (OnPlayerLootItem, OnPlayerCreateItem, OnPlayerQuestRewardItem, OnPlayerGroupRollRewardItem). The hooks carry the Player, so per-player decisions (stat pools) are possible.
3. **Quality roll → visible variant**: on award, a quality roll (rates table) picks a tier; the awarded item is SWAPPED to the visible variant of that tier — a real item_template row with scaled stats and its own quality color / name / item level. No backward variants: an item only gets variants of HIGHER quality (common → uncommon/rare/epic/legendary; uncommon → rare/epic/legendary; epic → legendary only). Artifact and heirloom qualities are excluded; legendary items get no variants. Loot tables are not modified — the swap happens in the module.
4. **Variant stat scaling**: ×1.75 compound per tier above the base quality — uncommon ×1.75, rare ×3.06, epic ×5.36, legendary ×9.38 — applied to armor, weapon damage, and each stat value. Variants are new item_template rows (this fork's item_template is a monolithic 144-column table; ~50–78k variant rows at full scale) with allocated entry ids; each variant copies the base row and mutates Quality + scaled stats (+ name per the naming item below).
5. **Statless items** (no stats/damage/spells — e.g. Flax Vest, armor-only): the variant template gets an added stat seed drawn from the SAME ×10 ilvl bands used for enchant magnitudes (10–30 points at ilvl 1-20 growing to ~400–600 at ilvl 241-277), from the class-appropriate stat pool. Note: the engineer referenced "300-600 at ilvl 260+" — pin the exact top band values in the spec table.
6. **Enchant magnitude engine**: a custom scaled enchant matrix — new rows in the `spellitemenchantment_dbc` DB mirror (schema: ID, Charges, Effect_1..3, EffectPointsMin_1..3, EffectPointsMax_1..3, EffectArg_1..3, Name_Lang_*) — generated as an ilvl-band × stat × magnitude matrix. Magnitudes are ×10 the original sketch: ilvl 1-20 → 10-30; 21-40 → 30-60; 41-70 → 60-100; 71-120 → 100-180; 121-180 → 180-280; 181-240 → 280-400; 241-277 → 400-600 (lay out the full band table; reconcile with "300-600 at 260+"). Each roll draws rand(min, max) within the band. Magnitude is then multiplied by a tier multiplier: tier1 ×1.0, tier2 ×1.15, tier3 ×1.35, tier4 ×1.6, tier5 ×1.9. **No total cap** on enchant contribution. Custom enchant ids require a client DBC patch for tooltip names (accepted; documenting the requirement is in scope, building the patch is not).
7. **Enchant count**: keep the module's chained per-slot roll (EnchantChance1 70% → EnchantChance2 65% → EnchantChance3 60%). MOVE the enchant slots from {0, 1, 5} to the PROP slots (PROP_ENCHANTMENT_SLOT_0..4 = 7–11, per Item.h) so random enchants do not collide with the TEMP slot used by rogue poisons and shaman weapon buffs — a latent bug in the current module.
8. **Enchant stat pools**: keyed by the LOOTING PLAYER's class. Four archetype pools with weights: CASTER (Int 35, Spell Power 30, Crit 15, Haste 12, Spirit 8), HEALER (Int 30, Spirit 25, MP5 20, Spell Power 15, Haste 10), PHYSICAL (Str/Agi 35, AP 20, Crit 15, Haste 12, Hit 10, Expertise 8), TANK (Stamina 40, Str 20, Defense 15, Dodge/Parry 10, Hit/Expertise 15). Weapon pools: WEAPON-caster (Int 40, SP 30, Haste 15, Crit 15), WEAPON-melee (Str/Agi 40, AP 25, Crit 15, Haste 10, Expertise 10), WEAPON-hunter (Agi 40, AP 30, Crit 15, Hit 15). JEWELRY pool (class primary 50 / secondary 30 / utility 20) and RELIC pool (class primary only). The weapon pool is chosen from the weapon's own stat profile (int/spell power → caster; agi → agi/hunter; str → melee).
9. **Class → archetype mapping** (fixed, config-tunable; spec-aware talent-tree selection is a v2 refinement): mage, warlock → CASTER; priest, druid, shaman, paladin → HEALER; warrior, rogue, hunter, death knight, retribution paladin, enhancement shaman, feral druid → PHYSICAL; protection warrior/paladin, feral bear, tank DK → TANK. Hybrid classes default to the pool named above; per-class overrides live in config/table.
10. **Rates**: a DB rates table — quality tier weights per ilvl band, plus the pool weights — tuned via SQL UPDATE + reload, no rebuild. Exact numbers are TBD by tuning; propose a starting table (e.g. low ilvl flatter, high ilvl heavily biased to low tiers so tier 5 stays rare).
11. **Known constraints to honor**: quality color/name/item level are template-level (the client caches item query responses by entry) — hence variants must be real rows, never per-instance overrides. DBC data source is deployment-dependent (LOAD_DBC takes a file and a DB mirror; the randproppoints_dbc / itemrandomsuffix_dbc mirrors are EMPTY in this dump) — the spec must include a runtime verification step (which source the server actually loads: .dbc files under the server data path vs the DB mirrors) BEFORE any DBC data is populated.
12. **Open implementation items** (flag each with a recommended default): (a) variant name generation — "Superior/Exquisite/Regal…" prefix map vs "(Epic)" suffix (recommend a prefix map); (b) swap timing — post-pickup swap shows the base name in the loot window, a loot-roll-time swap shows the variant (recommend post-pickup for v1, note the loot-window nuance); (c) rates-table reload mechanism — a .reload hook vs read-per-roll (recommend read-per-roll for v1, cache with reload later); (d) client DBC patch generation for matrix enchant names (document the process, do not build).
